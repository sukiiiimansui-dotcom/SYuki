# 03 · 地图渲染方案：代码绘制，不用图像生成模型

## 结论先行

**地图全部由代码确定性渲染**（服务端 Python + PIL），**刻意不使用图像生成模型**。

## 为什么不用生图模型

| 维度 | 代码绘制 | 图像生成模型 |
|---|---|---|
| 可复现 | ✅ 相同输入必得相同输出，可"重画" | ❌ 每次不同，难复现 |
| 地理准确 | ✅ 严格贴合 GeoJSON 边界 | ❌ 位置不可信，无法与定位对齐 |
| 体积 | ✅ 900×900 约 **8-25 KB** | ❌ 通常数 MB |
| 速度 | ✅ 缓存后 **60-170ms** | ❌ 秒级到十秒级 |
| 可缓存 | ✅ 按 `{adcode}_{style}` 缓存 | ❌ 每次都要重新生成 |
| 可交互 | ✅ 边界即数据，可直接做命中/下钻 | ❌ 像素图无法下钻 |
| 离线可用 | ✅ 只需 GeoJSON | ❌ 需模型服务 |

对地图这个场景，"位置对不对"是底线需求：用户定位在某区县，地图就必须真的是那个区县。
生图模型无法保证这一点，且每次结果不同会让"地图库"没有意义。

## 渲染流程

```
GeoJSON 边界
  → 逐点投影到画布坐标（统一坐标系统）
  → PIL 绘制：填充 + 描边（相邻区划共享边界，天然无缝）
  → 按层级叠加标注（省/市/区县名，字号随层级）
  → 输出 PNG
```

**关键细节**：

1. **相邻区划共享边界**：GeoJSON 里相邻区县的边界点是一致的，因此各画各的填充后，边界自然吻合，不需要额外拼接处理；
2. **标注随层级**：省级字号 13px、市级 12px、区县 11.5px；面积过小的区划过滤掉标注避免重叠；
3. **分辨率倍率**：`scale=1/2/3` 对应 1200×900 / 2400×1800 / 3600×2700；`scale≥3` 时关闭标注防重叠。

## 四种风格（可切换）

| 风格 | 特点 | 适用 |
|---|---|---|
| `gaode` 高德浅色 | 米白陆地 + 淡蓝水体 + 柔和描边 | 默认，接近地图 App 观感 |
| `dark` 深色夜景 | 深蓝底 + 亮青描边 + 光晕 | 夜间/沉浸 |
| `water` 手绘水彩 | 米白纸底 + 暖色描边 | 文艺风格 |
| `rpg` RPG 街区 | 绿地底 + 像素格纹理 | 小区层，游戏感 |

## 分级策略（手机内存友好）

| 区域 | 分辨率 | 大小 |
|---|---|---|
| 全国 / 省 / 市 | 1200×900（scale=2 时 2400×1800）| 8-25 KB |
| 城市拼接大图 | 1200×900 → 3600×2700 按需 | 20-90 KB |
| 小区街区 | 900×900 | 8-15 KB |

对比：一张矢量瓦片包或高分辨率卫星瓦片动辄数 MB；
这里**所有地图都是几十 KB 的 PNG**，手机加载与内存压力极小。

## 缓存与预生成

- 路径：`images/{adcode}_{style}.png`（拼接大图另有 `bigmap/{adcode}_{style}_{scale}.png`）
- 命中缓存直接返回文件（**60-170ms**）；未命中才渲染并写缓存
- 启动时后台**预生成**常用区域（已预生成 106 张）
- 数据侧同样缓存：省市县 GeoJSON 已全部预缓存（34 省 **0 失败**）

## 可选：真实地物参考

小区层可选择性接入 **OpenStreetMap / Overpass** 拉取真实建筑与道路，作为 LLM 生成的参考（提升真实感）。
但 Overpass 公共服务器较慢（实测单次约 19 秒）且偶发超时，因此采用：

- **只读缓存，不阻塞**：生成时若本地已有该区域 OSM 缓存则用作参考，没有就用纯 LLM，不发起网络请求；
- **后台预热**：需要时后台慢慢拉取并缓存。

> 原则：**任何外部慢数据都不能阻塞用户操作**。
