## 一、先回答最关键的问题：**哪个分支 比 哪个分支**

```
head（我们这边要提的分支）              base（要求官方拉进哪个分支）
─────────────────────────────         ──────────────────────────────
sukiiiimansui-dotcom/LingChat          SlimeBoyOwO/LingChat
  └─ feat/world-map                      └─ dev          ← 注意：不是 main
       （fork 里，从 fork 的 dev 切出）
```

**base = `dev`，不是 `main`。** 证据（实测）：

| 证据 | 数据 |
|---|---|
| 最近合并的 PR 目标分支 | `dev` × 23，`main` × 0 |
| 当前开放的 PR 目标分支 | `dev` × 23，`main` × 3 —— 那 3 个全是维护者自己的热修（如 `SlimeBoyOwO:fix/persistent-memory-phase1`） |
| 两个分支的活跃度 | `main` 停在 **2026-09-01**（`ef8f7914`，= 0.5.1 发布点）；`dev` 已经到 **2026-09-11**（`957f3ad8`），领先 main 24+ 提交 |

也就是说：**`main` 是发布分支，`dev` 才是开发分支**，社区 PR 一律进 dev。

**head 必须是 fork 的分支**，原因：
- GitHub 只接受「同仓库分支」或「**fork** 的分支」作为 PR head；
- 我们的 `SYuki` 仓库与官方是**两段互不相连的历史**（当初是独立导入的快照，不是 fork），
  从 SYuki 的分支提 PR，GitHub 会按"无共同祖先"算出整个仓库重写，根本没法 review。

**好消息：fork 是服务端复制，秒级完成，不需要我们上传官方几万个历史对象。**

## 三、PR 里到底放什么（内容与组织）

### 3.1 文件白名单（当前 17 个，都是"纯新增 + 纯接线"）

| 类别 | 文件 | 行数 |
|---|---|---|
| 数据层 | `src/api/services/worldMap.ts` | 213 |
| 页面 | `src/components/views/WorldMap.vue`、`WorldMapLayer.vue` | 845 |
| 状态 | `src/composables/useWorldMap{Layer,Bindings,Modules,Tick}.ts` | 403 |
| 挂载（**纯新增**） | `src/App.vue`(+4)、`MainMenu.vue`(+1)、`MainMenuOptions.vue`(+4)、`router/index.ts`(+6) | 15 |
| Rust 侧（待搬） | `src-tauri/src/world_map/*.rs`（14 个模块） | ~9300 |

**减法（进 PR 前必须做）**：删掉 `public/world_map/*.js`（5 个文件、5668 行）。
它们是 Python 原型的浏览器脚本，官方 PR 里是纯负担；改由前端直接调 Rust 命令。
这一步能把 PR 体量砍掉近一半，也让 review 容易得多。

### 3.2 commit 组织（建议 3 个，语义清晰）

1. `feat(world-map): 地图数据层与图层组件`
   —— `worldMap.ts` + `WorldMapLayer.vue` + composables + `App.vue` 接线
2. `feat(world-map): 地图页面与入口`
   —— `WorldMap.vue` + router + 主菜单入口
3. `feat(world-map): Rust 侧世界地图模块与命令`
   —— `src-tauri/src/world_map/*` + `lib.rs` 命令注册 + `Cargo.toml`

> 拆开的好处：维护者可以逐个看、逐个小步反馈；万一某个模块有异议，砍掉它不影响前两个。

### 3.3 **零新增依赖**改造（重要，直接影响能否被接受）

官方已有 `sha2` 与 `chrono`，我们只要把两处替换掉，**PR 就不需要新增任何 crate**：

| 现在用的 | 用途 | 改成 | 理由 |
|---|---|---|---|
| `md5` | 稳定随机种子（details/sketch/maplib/schedule） | `sha2`（官方已有）取前 16 字节 | 种子只要"稳定且散得开"，用哪个哈希无所谓 |
| `libc` | `localtime_r` 取设备本地时间 | `chrono::Local::now()`（官方已有 chrono） | 少一个平台相关依赖，跨端更稳 |

### 3.4 PR 描述（模板，中文 + 英文摘要）

```
## 这个 PR 做了什么
世界地图系统：按用户定位分层确定场景（国→省→市→区县），
AI 实时生成街区 SVG，角色按日程出现在该去的地方。（专为手机端设计）

## 为什么值得合
- 与现有架构零冲突：Rust 侧只新增模块 + 注册命令；前端只新增页面 + 4 处纯新增接线
- 不引入新依赖（复用已有的 sha2 / chrono / reqwest / rand）
- 离线可用：行政区划走本地 geojson 缓存，OSM 只作可选增强，LLM 不可用时降级为本地草图
- 手机端优先：SVG 渲染（几百 KB、毫秒级）、可缩放不糊、中文交给系统字体

## 怎么验证
- `cargo test --lib world_map` —— 130 个单测
- `npx vue-tsc --noEmit --skipLibCheck` —— 0 error
- 手动：主菜单「世界」→ 定位 → 点区划下钻 → 「实时绘制」看 AI 逐栋画

## 影响面 / 回滚
- 只新增文件 + 4 处挂载点（合计 +15 行，**不删改官方任何一行**）
- 回滚 = revert 这一个 PR，无数据迁移、无配置变更

Refs #804
```

## 四、提交动作（用 API，因为 git 通道不通）

```bash
# ① 建 fork（服务端复制整个仓库，含官方全部历史；不上传任何东西）
curl -X POST -H "Authorization: token $TOKEN" \
  https://api.github.com/repos/SlimeBoyOwO/LingChat/forks

# ② 让分支基于 **dev**（fork 的 dev 与上游自动同步）
#    取 fork 的 dev HEAD sha → 用它当 base_tree 的 commit
curl -s -H "Authorization: token $TOKEN" \
  https://api.github.com/repos/sukiiiimansui-dotcom/LingChat/commits/dev

# ③ 用 Git Data API 把地图文件写成一个 commit（只传改动文件，不是整个仓库）
#    已有脚本可复用：~/rikka/Dsh-SYuki/scripts/push_via_api.py
python3 .../push_via_api.py --repo sukiiiimansui-dotcom/LingChat \
  --base <fork 的 dev sha> --branch feat/world-map --files <白名单文件>

# ④ 开**草稿** PR（draft 先行，避免打扰维护者）
curl -X POST -H "Authorization: token $TOKEN" \
  -d '{"title":"feat: 世界地图系统（分层地理 + AI 生成街区，手机端优先）",
       "head":"sukiiiimansui-dotcom:feat/world-map","base":"dev","draft":true,
       "body":"…见 3.4 模板…"}' \
  https://api.github.com/repos/SlimeBoyOwO/LingChat/pulls
```

## 五、本地怎么配合（两条线的定位）

| | 用途 | 基线 | 说明 |
|---|---|---|---|
| 线 A `feat/world-map`（`~/lingchat-main`） | 我们自己的 L-SYuki 产品线 | 我们 SYuki main | 可以自由加 SYuki 定制、web-mock、pnpm 版本适配 |
| 线 B `feat/world-map-official`（`~/lingchat-official`） | **PR 的素材库**，证明"只差地图" | 官方 main 快照 | 用门禁脚本卡住 |
| fork 的 `feat/world-map` | **真正提 PR 的分支** | 官方 **dev** | 由 API 生成，不必本地维护 |

**为什么本地线 B 保持 main 而 PR 用 dev**：本地拿不到 dev 的新提交（git 通道不通，本地 `upstream/dev` 只到 09-04），
而 fork 里的 dev 与上游自动同步 —— 所以"重放到 dev"这一步**在 fork 里做**，比在本地硬凑更可靠。
本地线 B 的职责是**证明改动范围纯净**（门禁）+ 作为素材源头。
